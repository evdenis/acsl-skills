# Anatomy of a WP Coq goal

## Where the file comes from

```sh
# Resolve the toolchain (auto-detects the opam switch holding frama-c;
# override with FRAMAC_SWITCH=<name>). The wrapper scripts do this for you.
. frama-c-wp/scripts/env.sh

frama-c ... -wp-prover coq -wp-interactive update -wp-session S file.c
```

writes `S/interactive/<goal>.v`. The goal id is `lemma_<name>` for an ACSL `lemma`, or
`typed_<function>_<clause>` for a function goal.

Modes for `-wp-interactive`:

| Mode | Behaviour |
|---|---|
| `batch` | check the existing script; **do not** create one. This is the CI/check mode. |
| `update` | regenerate the preamble from the current source, keep the proof, then check |
| `edit` | open an editor (interactive only — not usable headlessly) |
| `fix` | check, and open an editor if it fails |
| `fixup` | update, check, and open an editor if it fails |

Use `update` to create or refresh, `batch` to verify.

## The edit contract

```coq
(* This file is generated by Why3's Coq driver *)
(* Beware! Only edit allowed sections below    *)
Require Import BuiltIn.
...                            <- generated preamble: memory model, your ACSL definitions
(* Why3 goal *)
Theorem wp_goal :
  forall (t:addr -> Z) (a:addr) (i:Z), ... .
(* Why3 intros t a i h1 h2. *)  <- the raw auto-generated names
Proof.
  ...                          <- YOUR PROOF GOES HERE, and only here
Qed.
```

**Only edit between `Proof.` and `Qed.`.** `-wp-interactive update` rewrites everything above
and any edit there is destroyed.

The `(* Why3 intros ... *)` comment shows the raw hypothesis names. Re-`intros` with
meaningful ones instead — `intros K L a i k n. intros kUpper kLower iNN L32 K32.` — which
makes the proof readable and survives regeneration.

## Name mangling: ACSL to Coq

| ACSL | Coq |
|---|---|
| `logic integer Count(...)` | `L_Count` |
| `predicate Unchanged{K,L}(...)` | `P_Unchanged` |
| `lemma Count_Union: ...` | `Q_Count_Union` — available as a hypothesis in other goals |
| `axiom sum0: ...` | `Q_sum0` |
| overloaded definition | suffix `_1_`, `_2_` in declaration order: `L_Count_1_`, `P_AllEqual_2_` |
| definition body | `L_Count_1__def` |

So the lemmas you already stated in `.acsl` are usable inside a Coq proof as `Q_<name>` — that
is what keeps these proofs short. Check the preamble for the exact spelling before using one;
the `_1_` suffixes are easy to get wrong.

## Typed memory model vocabulary

Goals are stated in the model's primitives, not in C terms. The ones that actually appear:

| Symbol | Meaning |
|---|---|
| `addr` | an address: a `base` plus an `offset` |
| `base p`, `offset p` | the two components |
| `shift p k` | `p + k` in pointer arithmetic |
| `t : addr -> Z` | a **memory chunk** — the array of int-typed memory. Two states appear as two chunks `t` and `t1` |
| `is_sint32 v` | `v` fits in `int` |
| `is_sint32_chunk t` | every cell of chunk `t` fits in `int` |
| `to_sint32 v` | truncation to `int` |
| `valid_rd`, `valid_rw` | `\valid_read` / `\valid` |
| `separated`, `included` | `\separated` and range inclusion |
| `region`, `global` | base classification |

A two-state ACSL predicate `Unchanged{K,L}(a,m,n)` arrives as `P_Unchanged_1_ t t1 a m n` with
`t` the `K` chunk and `t1` the `L` chunk. Naming your `intros` after the ACSL labels (`K`, `L`)
keeps this legible.

## Typical goal shape

```coq
Theorem wp_goal :
  forall (t:addr -> Z) (t1:addr -> Z) (a:addr) (i i1:Z),
  is_sint32_chunk t1 -> is_sint32_chunk t -> is_sint32 i ->
  P_Unchanged_1_ t t1 a 0%Z i1 ->
  ((L_Accumulate t1 a i1 i) = (L_Accumulate t a i1 i)).
```

Read it as: for two memory states whose int cells are in range, if the range is unchanged
between them, then the logic function agrees on both.

The `is_sint32*` hypotheses are almost always needed by `lia` later — `intros` them with names
like `L32`, `K32` and pass them to `auto with zarith`.
